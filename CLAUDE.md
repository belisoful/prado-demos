# CLAUDE.md

This file provides guidance to Agents when working with code in this repository. It is
the fast-path memory file; the full guidelines are in [`AGENTS.md`](AGENTS.md).

## What This Is

`pradosoft/prado-demos` — a collection of example **PRADO applications** that depend on
`pradosoft/prado` (`^4`) via Composer. This repo has **no framework source**; do not
apply framework build/lint/test workflows here.

The star app is `quickstart` — the framework's end-user documentation (267 `.page`
files).

- Target PRADO version: **4.3.3**. The installed framework at `vendor/pradosoft/prado`
  is the source of truth for every technical claim; a sibling checkout of the framework's
  release branch may be symlinked in its place while a release is documented.

## Commands

```bash
composer webserver        # serve all demos at http://127.0.0.1:8080 (php -S ... -t ./)
composer webserver:stop   # stop it
php -S localhost:8080 -t quickstart   # serve one app

# rebuild the quickstart Lucene search index
cd quickstart/protected/index/ && php QuickstartIndex.php
```

- Per-app `assets/` and `protected/runtime/` must be web-writable (`composer
  install`/`update` chmod them).
- No `phpunit`/`phpstan`/`php-cs-fixer` in this repo. Verify by rendering pages and the
  documentation audits below.

## Repo Layout

Each `<app>/` is a self-contained PRADO app: `index.php` (requires `../autoload.php`,
`new \Prado\TApplication`, `->run()`), `assets/`, `themes/`, `protected/` (with
`application.xml`, `pages/`, `controls/`, `runtime/`). `autoload.php` (repo root) is a
shared Composer-autoloader shim covering standalone, copied-vendor, and symlinked-vendor
layouts. The quickstart TOC is `quickstart/protected/controls/TopicList.tpl`.

## Quickstart Documentation Rules

Match the existing page idiom and the enforced writing style (full detail in AGENTS.md):

- Idiom: `<com:TContent ID="body">`, `<h1>/<h2>/<h3>`, `<p class="block-content">`,
  `<com:TTextHighlighter CssClass="source block-content">`, `<tt>`, and
  `<com:SinceVersion Version="X"/>` / `<com:RequiresVersion Version="X"/>` badges. Add
  new pages to `TopicList.tpl` (a page is navigable only if listed there).
- **Every XML configuration example is followed by its PHP equivalent**, with this glue
  text between them, verbatim and on one line:
  `<p class="block-content">The same configuration in the PHP format:</p>`
  Never leave an XML configuration block unpaired. Full detail under
  [XML and PHP Configuration Pairing](#xml-and-php-configuration-pairing) below.
- **Badge at the true introduction version**, section-level where a page spans versions.
  Never exceed 4.3.3.
- **Scope ceiling 4.3.3** — exclude 4.4.0 material (PSR-3 logging: `TPsrLogger`,
  `TPsrLogRoute`, `psr/log`).
- **Style (enforced):** American English, present tense, timeless, SVO declaratives,
  `condition → result` tables. Banned: antithesis ("not just X, it Ys"), em-dash
  dramatic asides, editorializing/filler, rule-of-three lists. One fact per sentence.
- **Diagrams:** a structural subject (hierarchy, flow, lifecycle, precedence) gets an
  SVG generated by a committed stdlib-only Python script under `tools/diagrams/`, wired
  as `<img src="<%~name.svg%>" class="figure" alt="…">`. Render it to pixels, view it,
  and iterate until it is approved; every box and edge is verified against the framework.

## Source of Truth & Verification

Verify every technical claim against the installed 4.3.3 framework at
`vendor/pradosoft/prado`, in order: class docblocks in `framework/**` → Working
Knowledge `agents/framework/**` (`INDEX.md`/`SUMMARY.md`/`<Class>.md`) → `HISTORY.md` →
code + `tests/unit/`. `framework/classes.php` is the canonical class list. Configurable
module classes carry XML+PHP config examples in their docblocks (copy verbatim).
Verification recipes, the version → feature map, the diagram procedure and the framework
behaviors the pages work around are in [docs/quickstart-maintenance.md](docs/quickstart-maintenance.md).

**The `agents/` Working Knowledge base is ~95% accurate — verify before use.** When it
is wrong, do not edit the framework repo; record the path, the false claim, the code
evidence, and the correction in `local/framework-agents-kb-inaccuracies.md`. Record a
behavioral bug found in the framework code itself in `local/framework-code-bugs.md`.

## XML and PHP Configuration Pairing

Every configuration example in the quickstart shows both formats. An XML block is followed
immediately by the standardized line and the PHP block:

```html
<com:TTextHighlighter Language="xml" CssClass="source block-content">
...
</com:TTextHighlighter>
<p class="block-content">The same configuration in the PHP format:</p>
<com:TTextHighlighter Language="php" CssClass="source block-content">
...
</com:TTextHighlighter>
```

The connector text is fixed: `The same configuration in the PHP format:`. Use it verbatim so
the pairing is greppable. A whole-file example opens with `<?php` and `return [`; a fragment
shows only the keys that the XML fragment covers.

- Shape: a repeating XML element becomes an array keyed by `id`, and that element's
  attributes become its `properties` array. A module that nests further elements reads them
  from a key of its own: `routes` (`TLogRouter`), `urls` (`TUrlMapping`), `jobs`
  (`TCronModule`), `behaviors` (`TBehaviorsModule`), `users` and `roles` (`TUserManager`),
  `permissionrules` (`TPermissionsManager`), `translate` (`TGlobalization`), `soap`
  (`TSoapService`), `database` (`TDataSourceConfig`). Page configurations add `authorization`
  and `pages`. The `lazy` flag goes inside `properties`.
- **Key case is a trap.** The XML branch of several loaders calls `array_change_key_case()`
  and the PHP branch does not, so the PHP keys must be exactly lowercase where the loader
  reads a lowercase constant: cron jobs take `name`/`schedule`/`task`/`username`, permission
  rules take `name`/`action`/`users`/`roles`/`verb`/`ips`/`priority` under a
  `permissionrules` key, and behaviors take `name`/`class`/`attachto`/`attachtoclass`/
  `priority`. A property that reaches `setSubProperty` keeps its own capitalization. The
  framework docblocks get this wrong for cron.
- **Four things have no working PHP form in 4.3.3**, and the pages say so rather than
  showing an example that fails: `TRpcService`, `TSoapService`, the `<server>` pool of
  `TMemCache`, and the application-level `includes` key. SqlMap mapping files are XML in
  both formats by design.
- Not every XML block is configuration. Template markup uses `Language="prado"`, and an
  XLIFF catalogue or a SqlMap mapping file is neither.
- Verify a new pair by loading both forms through the real configuration loaders and
  comparing the resulting arrays.

## Known Legacy Issues and Traps

- The `sqlmap` manual app is the one documentation set left unpaired. Its single PRADO
  configuration example (`Manual/Tutorial/TestSecond.page`) declares `TSQLMap` with a nested
  `<provider class="TAdodbProvider">`, from the PRADO 3.0 data-access API. None of those
  classes exist in 4.3.3, so a PHP counterpart would assert a shape that cannot be verified.
  That app needs its own correctness pass before it is paired. Its other 57 XML blocks are
  SqlMap mapping files, which are XML under both configuration formats. It also carries
  pre-existing paragraph-markup defects.
- `blog-tutorial` and `site` carry pre-existing paragraph-markup defects that the quickstart
  pass cleared in the quickstart only.
- Coverage gaps, measured against the shipped classes: `TArrayHelper` and `TBitHelper`
  (`framework/Util/Helpers`) are undocumented, and `Prado\Xml` is named only in passing on
  `Configurations/AppConfig.page`. Neither is large enough to warrant a page of its own;
  fold them into `Advanced/Utilities.page` if they come up.
- The demo `protected/application.xml` files, `sqlmap/protected/pages/Manual/config.xml`,
  five `blog-tutorial` `.page` files, and the `README.md` config example still use
  pre-namespace `class="System.*"` aliases, which run via 4.x backward-compat aliasing.
  Quickstart prose and examples use `Prado\…` paths; modernize the rest when touched.
- Version strings: use `<com:SinceVersion>` for a feature's release and
  `<com:CurrentVersion />` when a page must show the running version. The
  `Upgrading32/33` mentions are historical and stay.
- Database driver support is enumerated in three places that do not agree, and each was
  verified from its own dispatch table: Active Record metadata
  (`Data/Common/TDbMetaData.php`), scaffold input builders
  (`Data/ActiveRecord/Scaffold/InputBuilder/TScaffoldInputBase.php`) and the
  `TDbDriver` constants. Each dispatch falls back to a global event
  (`fxDataGetMetaDataClass`, `fxActiveRecordScaffoldInputClass`) so an extension can add a
  database. Read the switch before stating what is supported.
- `GettingStarted/NewFeatures.page` and `Upgrading.page` render `HISTORY.md` and
  `UPGRADE.md` from the installed package, so they never go stale. Keep that render
  mechanism as is. `NewFeatures.page` also carries an authored "The 4.x subsystems"
  table above the render (subsystem, release, page); when a page documenting a 4.x
  subsystem is added or renamed, update that table.
- WSAT moved out of the framework in 4.2.0 into `pradosoft/prado-wsat` and is not
  installed here, so its screens cannot be exercised. Its page lives at `Advanced/Wsat.page`
  beside Extensions, and is written as core documentation because the tool is still
  expected to be documented in the framework's own docs. Its service class name and install
  step are unverified against the current package.
- Paragraph markup: keep tags balanced, and never enclose a block element in a paragraph.
  HTML closes a paragraph at a block element, so a `<com:TTextHighlighter>`, `<ul>` or
  `<table>` written inside one renders an empty paragraph and strips the class from the
  prose after it. Keep code samples, lists and tables outside paragraphs; open a fresh
  paragraph for the prose that follows.
- `<com:SinceVersion>` renders its own `<p>`, so a badge written inside a paragraph nests
  one paragraph in another. The browser closes the outer one at that point, splitting the
  text and dropping its styling. Put the badge on its own line above the paragraph or
  heading it dates, never inside one, and never two in a row.
- Hyphenated HTML attributes (`aria-*`, `data-*`) cannot be set from a template in 4.3.3.
  Both template forms fail, one loudly and one silently. Use the `Attributes` collection in
  code. Documented on `Configurations/Templates1.page`.
- Deprecated properties are a recurring trap. HTML5 obsoleted the attributes behind
  `TImage.ImageAlign`/`DescriptionUrl`, `THyperLink.ImageAlign`/`ImageHeight`/`ImageWidth`,
  `TTable.CellSpacing`/`CellPadding`/`GridLines`, `TTableHeaderCell.CategoryText`,
  `TDataList.CaptionAlign`, `TTableItemStyle.HorizontalAlign`/`VerticalAlign` (which
  reaches every `ItemStyle`/`PagerStyle`/`HeaderStyle` on the data controls), six
  `TInlineFrame` properties, and `TMetaTag.Scheme`. Grep `@deprecated` in
  `framework/Web/UI/**` before documenting a property as the way to do something, and name
  the CSS or ARIA replacement.
- Bare class names in configuration and page code (`class="TAuthManager"`,
  `class Home extends TPage`) resolve through 4.x aliasing and are how the demo apps are
  written; they are not defects. `Prado::using('System.…')` imports of framework classes
  are unnecessary (the framework autoloads) and are replaced by `use` statements when
  touched; `Application.…` paths for an app's own classes are still needed.

### Dating a `SinceVersion` badge

A badge dates the release that first shipped the thing the section describes. It does not
date the commit that later touched the file, and it does not date the class when the section
documents a property added to that class years afterward.

Resolve it in this order, and stop at the first answer the next step does not contradict.

1. The `@since` line on the class, method or property itself. 778 files carry one.
2. The release section of `HISTORY.md` that announces the symbol by name. This beats
   `@since` when the two disagree: `TActiveMultiView` claims `@since 3.1.6` and shipped in
   3.1.9.
3. The introducing commit, `git log -S<symbol> --pickaxe-regex --reverse --all` with the
   symbol wrapped in `[^A-Za-z0-9_]` so a longer name does not match, then the earliest
   release in `HISTORY.md` dated after that commit whose tag contains it.

The framework repository has full history to 2005, but its tags are sparse (no 3.1.1,
3.1.3, 3.1.6-3.1.10, 3.2.1 and others). Tag-only lookups under-report; date-only lookups
over-report, because a trunk commit is often released two or three versions later than the
next dated release. Never write a version string for something that is not a shipped
release: `3.1a`, `3.1b`, `3.1rc1` and `3.2a` appear in framework `@since` lines and belong
in a badge as `3.1` and `3.2`.

## PRADO Naming Conventions

Classes `TPascalCase`; methods/variables `camelCase`; class properties `_camelCase`;
class constants `SCREAMING_SNAKE_CASE`; enumerated constants `PascalCase`; namespaces
`Prado\{Module}`; pages `.page`+`.php`; portlets/masters `.tpl`+`.php`; control tags
`<com:`.

## Anti-Patterns (Required Safeguards)

- **Never** run `git clone/mv/restore/rm/branch/commit/merge/rebase/reset/pull/push`
  without developer approval first.
- **Never** run `rm` on any path without developer approval first.
- **Never** remove Composer `--dev` dependencies.
- **Never** erase or overwrite files whose changes are the subject of the current task.
- **Never** modify the framework repository (any sibling checkout) or its `agents/`
  knowledge files from a session in this repository; record corrections under `local/`.
